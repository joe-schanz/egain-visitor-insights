# Decision Log

Every meaningful design choice, what was rejected, and why. Numbers come from
`data/processed/cleaning_report.json` (regenerated by the pipeline).

---

## D-001 · Zero-cost stack
**Decision:** Python data pipeline → precomputed JSON → static React site on Vercel (free Hobby plan).
**Rejected:** Streamlit Cloud / Render free tiers (sleep after inactivity, 30s+ cold start, risky for a
link that must stay live 15 days); a hosted database (unnecessary for ~14 days of logs).
**Why:** The data is a fixed historical log, so all heavy work can happen offline once. A static site
cannot go down, loads instantly, and costs nothing. In production the same pipeline would run on a
schedule (e.g. nightly) against the live log stream.

## D-002 · Parquet as the working format
**Decision:** Convert the 530K-row .xlsx to Parquet once (`01_load.py`).
**Why:** Excel parsing takes ~60s per run; Parquet loads in <1s and keeps types. Fast iteration on
the cleaning rules mattered more than anything else.

## D-003 · The data has a 10-day hole
**Finding:** No hits between 2025-02-10 00:17 UTC and 2025-02-20 00:17 UTC. Both blocks start at
00:17 and end at 00:16, so this is two exports joined (Feb 1–10 and Feb 20–25), ~14 days of real data.
**Action:** Asked the recruiter whether a second file exists. **Confirmed: there is no second file;
the gap is part of the dataset.** So:
- Trend charts show the gap explicitly (a visible break, not a line drawn across it) so nobody reads it
  as a traffic collapse.
- Daily averages divide by the ~14 days actually covered, not the 24-day calendar span.
- All "recency" logic is measured against the last timestamp in the data (2025-02-25), not today's date.
- `01_load.py` still loads every .xlsx in `data/raw/`, so new log exports drop in with no code change.

## D-004 · Page taxonomy with intent weights
**Decision:** Hand-written, ordered regex rules (`pipeline/taxonomy.py`) map each URL to one category
with an intent weight (0–10), plus topic tags (industry, integration platform, product).

| Category | Weight | Examples |
|---|---|---|
| conversion | 10 | /contact-us/, /forms-request-demo/, /risk-free-trial… |
| integration | 7 | /egain-for-servicenow/, /knowledge-management-software-for-genesys-cloud/ |
| product, proof | 6 | /ai-knowledge-hub/, /success/…, Gartner/Forrester pages |
| industry, solutions | 5 | /knowledge-management-in-banking/ |
| webinar | 4 | /company/events/, *webinar* |
| resource | 3 | /resources/…, white papers |
| education, topic content, partner, customer | 2 | /blog/, /what-is-… |
| home, company, news | 1 | /, /company/news/… |
| noise | 0 | investors, careers, opt-out, copyright, feeds |

**Rejected:** ML topic clustering (unexplainable to a rep, overkill for ~3K unique pages).
**Why:** A rep (and an interviewer) can read every rule. Integration pages are weighted high because
they reveal the prospect's **tech stack** (e.g. "they use Genesys"), which is gold for discovery.
Press releases are checked *before* integrations because they mention partner names without
signalling evaluation. Investor/careers traffic is real but not buyer traffic.

## D-005 · Bot & machine traffic removal (rule-based, layered)
**Decision:** Each hit gets exactly one `traffic_class`, first rule wins. Results on the Feb 2025 file:

| Class | Hits | Rule |
|---|---|---|
| bot_distributed | 120,263 | One browser signature on 100+ IPs, ≥95% one-page direct visits |
| email_scanner | 101,320 | Campaign-link clicks by security gateways / sandboxes (D-006) |
| bot_declared | 96,943 | User agent self-identifies (python, aiohttp, crawler, nagios, Barracuda…) or RSS feed |
| **human** | **95,547** | everything else (**18% of raw**) |
| crawler | 67,268 | 200+ distinct pages per IP, 30+ hits/min, 4+ pages at ≤2s pace, or 40+ pages in one visit |
| monitor | 45,001 | ≤3 pages polled 50+ times over 5+ days (uptime checks, an IR-page watcher) |
| probe / asset / legacy IE | ~4,000 | wp-admin/.php probes, open-redirect attempts (utm_medium=//bestbuy.com), static files, IE ≤ 9 |

**Rejected:** Off-the-shelf bot lists only (would have missed the two largest classes); ML anomaly
detection (no labels, unexplainable).
**Why:** The biggest bot populations disguise themselves as normal Chrome. They were caught by
*behaviour*, not by name:
- **Distributed bot:** 113K visits from 50,652 IPs, all with Chrome 124 on Windows, 99.99% one-page
  homepage hits. Chrome auto-updates; by Feb 2025 real users were on 131–133. No human population
  looks like this.
- **Rotating-UA scraper:** 50 browser strings from proxy ranges, pages loaded ~2 seconds apart.
- Thresholds were chosen by looking at the distribution of real browsers (current Chrome/Safari
  versions have 15–40% one-page-direct visits; the bot signatures sit at 95–100%).

## D-006 · Email campaign clicks: separating people from security scanners
**Finding:** 124K hits carry `utm_source=1on1&utm_campaign=…&uid=<GUID>`. The uid is a per-recipient
CRM contact ID (Dynamics-style GUID). Spikes on Feb 6 and Feb 20 match the campaign send dates.
**Decision:** A campaign click is a scanner, not a person, if any of:
1. The IP clicked links addressed to **5+ different contacts** (a person clicks their own email).
   1,155 gateway IPs, 79% of all campaign clicks.
2. **3+ campaign/opt-out hits from one IP in the same second** (scanners open every link in an email
   at once, including the opt-out footer).
3. Legacy Internet Explorer, or a scanner/bot user agent (Barracuda Sentinel, etc.).

**Contact status** (one row per uid):
- `engaged`: a human click, then a real follow-on page (not the landing page, not opt-out) ≥5s later.
  **151 contacts.**
- `clicked`: a plausible human click with no further browsing. **4,909 contacts** (unverified).
- `scanner_only`: only machine clicks. **40,676 contacts.** Email delivered, no evidence a human saw it.

**Why it matters for sales:** Raw marketing-automation reports would count ~46K "clickers". Only ~150
show provable human engagement. Reps chasing scanner clicks waste time; reps calling the 151 have a
real reason to call. This is the single most valuable insight in the dataset.

## D-007 · Visits (sessions)
**Decision:** Same IP + same user agent, new visit after 30 minutes of inactivity.
**Why:** The 30-minute timeout is the Google Analytics standard, so it's familiar and defensible. Without
cookies, IP + user agent is the best available visitor key. Corporate NAT can merge colleagues;
splitting by user agent reduces that.

## D-008 · What's still in the "human" set and handled later
- **Cloud/datacenter IPs** (AWS 3.x/44.x/52.x/54.x etc.) still show crawler-like visits. These get removed
  in the identification step using the IP owner's network type (D-010).
- **eGain's own employees** are flagged in identification (D-011).

## D-009 · IP → organisation: two free sources, cheapest first
**Decision:**
1. **IPinfo Lite database**, downloaded once (27 MB, free, unlimited) and queried locally. Gives the network
   owner (ASN name + domain) and country for every IP in milliseconds, no API limits.
2. **RDAP** (the modern WHOIS, run by the regional internet registries, free) for human visitors on ISP or
   unrecognised networks, highest intent first. ISPs often register which *customer* a block belongs to,
   e.g. a Verizon Business block registered to *GuideStone Financial Resources*, or an AT&T block to
   *Alberici Group*.

**Cost controls:** RDAP is rate-limited (~1 lookup/sec), so results are cached on disk and a single lookup
covers every IP in the returned block, but only when that is safe: small blocks (≤ 4,096 addresses) and
residential pools. Large business blocks are looked up per IP, because the ISP may have sub-assigned a
smaller piece to a named customer.

**Rejected:** Paid reverse-IP services (Clearbit Reveal / HubSpot, 6sense, Demandbase, KickFire, Dealfront):
much higher match rates, but they cost money. **They plug into exactly this step**; the rest of the
pipeline doesn't change. Reverse DNS: not used in this prototype. Corporate hostnames are uncommon on
modern networks, so RDAP was the better use of limited time. It's a reasonable next addition.

**Honest limitation:** Only IPs that a company *owns or has registered* can be named. Employees working from
home on Comcast, or behind Zscaler, can't be identified for free. That's the gap commercial
identity graphs fill.

## D-010 · Network type decides whether a visitor can be an account
**Decision:** Each network gets one type, from readable regex rules (`pipeline/networks.py`), checked in order:

| Type | Meaning | What the app does |
|---|---|---|
| egain | eGain's own offices/VPN | excluded (employees) |
| security_proxy | Zscaler, Netskope, Proofpoint … | counted as "enterprise user, company hidden" |
| hosting | cloud, datacenter, VPN, proxy farms, backbones | excluded from accounts (automation/anonymised) |
| organization | the IP block belongs to a named organisation | **becomes an account** |
| isp | consumer/business internet provider | account only if RDAP names a customer |
| unverified | none of the above | shown as low confidence |

**Order matters:** named hosting providers are checked *before* organisation words, so "Hurricane Electric"
(a backbone) isn't mistaken for a utility; organisation words are checked *before* generic network words,
so "Bank X Network Services" is still a bank.

**Finding:** Of ~25K human IPs, ~18K (73%) are hosting/VPN/proxy networks. Most of the traffic that slipped
past the bot rules is still machine or anonymised traffic. Only ~1% of IPs are directly-identifiable
organisations before RDAP. Organisations found directly include the IRS, JPMorgan Chase, Cisco, Bank of
America, Blue Cross Blue Shield of MA, US Dept. of Veterans Affairs, Duke Energy, NIH, Worldpay and
several banks, insurers, utilities and universities.

## D-011 · eGain's own traffic
**Finding:** The two highest-intent "ISP" visitors (140.89.x.x on Comcast) are in a block RDAP shows
registered to **EGAIN**. These are eGain employees and are excluded. Without this check, eGain's own
staff would have been the #1 "hot account" in the demo.

## D-012 · Secure web gateways are an enterprise signal, not noise
**Finding:** ~585 human IPs belong to Zscaler/Netskope. Large enterprises route employee browsing through
these, so the visitor is very likely a corporate user, but the gateway hides which company. The app
reports them as an aggregate ("enterprise visitors behind a security gateway") rather than throwing them
away. A commercial identity provider could often resolve these.

## D-013 · Proxy farms hiding behind company names
**Finding:** The first RDAP pass "named" companies like *Blazing SEO*, *Biterika Group*, *Big Sky Services*
and *OsoLabs*. These are residential-proxy and VPN resellers that rent IP blocks from ISPs and register
them in their own name. Their IPs each loaded one page and left.
**Decision:** An RDAP registrant only becomes an account if:
1. its own name doesn't classify as hosting / ISP / security vendor (same rules as D-010, plus a short
   list of proxy resellers seen in this log), and
2. it doesn't *behave* like a proxy farm: **5+ visitor IPs averaging ≤1.1 pages per visit** is relabelled
   hosting. Real companies have few IPs (one office NAT) and browse several pages.
**Why:** Without this, the top "accounts" by IP count were all proxy providers, which would discredit the
whole list in front of a rep. The behavioural rule catches farms that aren't on any list yet.

## D-014 · Firmographics from Wikidata, precision first
**Decision:** Industry, headcount, revenue and HQ come from **Wikidata** (free, open, CC0), through a handful of
batched SPARQL queries (`pipeline/04_enrich.py`). Matching, strongest first:
1. **Website match:** the network's domain (e.g. `duke-energy.com`) equals the organisation's official website
   on Wikidata. 106 accounts.
2. **Exact name match:** the cleaned registry name (legal suffixes removed) is exactly an English label or alias of an
   organisation-like item, *and* the countries agree (or the item is described as multinational). 29 accounts.
   The country check rejected *CSL Limited* (HK) → "Chinese Super League", *M1 Limited* (SG) → an Istanbul metro
   line, *ICT* (Nauru gov) → "Islamabad Capital Territory".
3. No match: blank firmographics, never a guess.

Every account also gets an **eGain sector** (Financial Services, Insurance, Healthcare, Government, Utilities, …)
from readable keyword rules over the name, domain and Wikidata industry. 205 of 234 accounts get a sector.

**Rejected:** Wikidata's search API (rate-limited after ~100 calls; batched SPARQL needs ~15 requests);
fuzzy name matching (too many confident-looking wrong companies); Clearbit/ZoomInfo/Apollo (paid; they plug in
here and would fill the 181 "size unknown" accounts).
**Why:** A rep who sees one obviously wrong company stops trusting the whole list. Blank beats wrong.
**Also tightened:** registry names that are pool or reserved labels, or contain long digit strings
("PPPoX Pool - Rback9", "BMF VoN OAM - RSVD"), and scanners/crawlers (Censys, Qwant, Hornetsecurity) are no
longer accounts.

## D-015 · Account score = Fit + Intent + Engagement (0–100), fully explainable
**Decision:** Every point has a reason the rep can read in the app (`pipeline/05_score.py`).

| Part | Max | Rules |
|---|---|---|
| **Fit** | 30 | Sector: eGain core vertical (financial services, insurance, healthcare, government, telecom, utilities, retail, travel) 15 · technology 8 · education 0 · other 4. Size: 10K+ employees 15 · 1K–10K 12 · 200–1K 6 · <200 2 · unknown 5 |
| **Intent** | 50 | Strongest signal per group, counted once: conversion page 20 · integration 10 · proof/analyst 8 · product 6 · industry/solutions 6 · webinar/resource 4 · education 2 |
| **Engagement** | 20 | 3+ visits 6 (2 visits 3) · 3+ people 6 (2 people 3) · 5+ distinct pages 4 · active in the final 7 days of data 4 |

**Tiers:** Hot ≥ 60 *and* a target sector (not education / unknown) · Warm 35–59 · Cold < 35.
**Guard rails:** accounts that look like competitors/partners (NICE inContact, Genesys …), job seekers (mostly careers
pages) or investors (mostly IR pages) are capped at 34 and flagged "review before outreach".
**Rejected:** a machine-learned score. With no closed-won labels there is nothing to train on, and a rep needs
to trust *why* an account is hot. In production, these weights would be tuned against pipeline outcomes from CRM.
**Dossier:** each account gets a one-sentence headline, talking points generated from rules (likely tech
stack from integration pages, product interest, industry story, buying-group size, linked CRM contacts, a
sector talk track) and a next action tied to the tier.

**Also:** two web domains belonging to one organisation (jpmchase.com, jpmorgan.com) merge into one account
through the shared Wikidata ID.

## D-016 · The web app
**Decision:** React + Vite single-page app reading four precomputed JSON files (`web/public/data/`, ~2.4 MB total;
accounts 0.6 MB). Recharts for the two stacked charts; simple CSS bars everywhere else. Deployed as static files on Vercel.
**Pages:** Accounts (search + filter by tier, sector, size, country, interest; sortable) → Account dossier (score
breakdown, talking points, next step, interests, visit timeline, identification evidence) · Email contacts (scanner vs
human per campaign; follow-up list) · Anonymous visitors (high intent, not identifiable for free) · Traffic & data
quality (funnel, daily traffic with the gap shown explicitly) · How it works.
**Choices:**
- Filters live in the URL (`/?tier=Hot&interest=Genesys`), so a rep can bookmark or share a view.
- Visitor IPs are masked in the UI (`16.98.8.x`); the product is about companies, not individuals.
- Light and dark themes follow the OS; layout works down to phone width.
- Partner-marketplace referrals (e.g. arriving from `appfoundry.genesys.com`) become a tech-stack talking point.
**Rejected:** a server/API (nothing to compute at request time); a component library (heavier, less distinctive).
